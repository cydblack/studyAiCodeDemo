1. 整体架构与逻辑

混合智能体把反应式（快、可调工具）和深思熟虑式（慢、多步分析） 放在同一张 LangGraph 里，由协调层 assess_query 根据用户问题决定走哪条路。

中层 · 协调

assess

评估 query_type / processing_mode，条件边分流

底层 · 反应式

reactive + tools

带工具的 LLM 循环，快速回答行情 / 配置 / 新闻类问题

顶层 · 深思熟虑

collect → analyze → recommend

三步流水线做深度投顾分析并生成建议文本

flowchart TD
  MAIN["__main__"] --> RUN["run_wealth_advisor"]
  RUN --> CREATE["create_wealth_advisor_workflow"]
  CREATE --> GRAPH["Compiled Graph"]
  RUN --> INV["agent.invoke(initial_state)"]
  INV --> ASSESS["assess_query"]
  ASSESS -->|reactive| RA["reactive_agent"]
  ASSESS -->|deliberative| CD["collect_data"]
  RA --> SCT{"should_continue_tools"}
  SCT -->|tools| TN["tool_node"]
  TN --> RA
  SCT -->|end| EXT["extract_reactive_response"]
  EXT --> END1([END])
  CD --> AN["analyze_data"]
  AN --> GR["generate_recommendations"]
  GR --> END2([END])

图 1 · 从入口到两条路径的总览

一句话：用户输入 → 评估分流 →（工具循环 或 三步分析）→ 写入 final_response → 结束。

class WealthAdvisorState(TypedDict):
    user_query: str
    customer_profile: Optional[Dict[str, Any]]
    query_type: Optional[Literal["emergency", "informational", "analytical"]]
    processing_mode: Optional[Literal["reactive", "deliberative"]]

create_wealth_advisor_workflow · 关键边
workflow.set_entry_point("assess")

workflow.add_conditional_edges(
    "assess",
    lambda x: "reactive_agent" if x.get("processing_mode") == "reactive"
              else "collect_data",
    {"reactive_agent": "reactive_agent", "collect_data": "collect_data"},
)

workflow.add_conditional_edges(
    "reactive_agent",
    should_continue_tools,
    {"tools": "tools", "end": "extract_response"},
)

workflow.add_edge("tools", "reactive_agent")
workflow.add_edge("extract_response", END)
workflow.add_edge("collect_data", "analyze")
workflow.add_edge("analyze", "recommend")
workflow.add_edge("recommend", END)

return workflow.compile()

10. 两条路径对照

反应式 reactive 深思熟虑 deliberative
触发 processing_mode == "reactive" 其他（通常 analytical）
节点序列 reactive_agent ⇄ tools → extract_response collect_data → analyze → recommend
LLM llm_with_tools 裸 llm
中间状态 messages market_data → analysis_results
最终字段 final_response（从 AIMessage 抽取） final_response（建议文本）
典型问题 行情、持仓比例、概念解释 组合调整、退休规划、教育金方案
两条路径互斥：一次 invoke 只会走其中一条，最终都在 final_response 汇合，方便 __main__ 统一打印。
CustomerProfile 与部分 current_phase / error 字段在本文件中定义了，但深思熟虑节点并未做严密的前置校验或错误回退图边； 实际分流完全由 assess 写出的 processing_mode 决定。

11. 常见知识点

补充理解运行入口、图是否随 query 变化、以及返回结果格式是否固定。

11.1 run_wealth_advisor 在做什么？

这是业务入口：组装初始状态，跑一遍 LangGraph，返回最终 state。 不负责命令行交互（交互在 __main__）。

run_wealth_advisor · 完整流程
def run_wealth_advisor(
    user_query: str, customer_id: str = "customer1"
) -> Dict[str, Any]:
    agent = create_wealth_advisor_workflow()
    customer_profile = SAMPLE_CUSTOMER_PROFILES.get(
        customer_id, SAMPLE_CUSTOMER_PROFILES["customer1"]
    )

    initial_state = {
        "user_query": user_query,
        "customer_profile": customer_profile,
        "query_type": None,
        "processing_mode": None,
        "market_data": None,
        "analysis_results": None,
        "messages": [],
        "final_response": None,
        "current_phase": "assess",
        "error": None,
    }

    print(agent.get_graph().draw_mermaid())  # 仅调试打印拓扑
    result = agent.invoke(initial_state)
    return result
步骤 说明
1. 创建工作流 create_wealth_advisor_workflow() 编译出固定拓扑的图
2. 取客户画像 按 customer_id 查 SAMPLE_CUSTOMER_PROFILES，找不到则用 customer1
3. 构造 initial_state 输入字段有值；中间字段为 None；current_phase="assess"
4. 打印 Mermaid draw_mermaid() 只输出图结构，不影响执行
5. invoke 从 assess 跑到 END，返回填好后的完整 state

11.2 图是每次一样，还是随 query 变化？

图的结构每次都一样；query 只决定走图里的哪条路，不会按问题重建一张新图。
  • 固定的是拓扑：入口始终 assess；反应式分支与深思熟虑分支的节点、边都在 create_wealth_advisor_workflow 里写死。所以每次 draw_mermaid() 打印出来的图长得一样。
  • 随 query 变的是路由：assess_query 根据问题写出 processing_mode；为 "reactive" 走反应式，否则走深思熟虑。 这是同一张图上的条件边，不是换图。 
flowchart LR
  Q["不同 query"] --> ASSESS["同一张图: assess"]
  ASSESS -->|reactive| PATH1["反应式路径"]
  ASSESS -->|deliberative| PATH2["深思熟虑路径"]
  PATH1 --> OUT["final_response"]
  PATH2 --> OUT

类比：地铁线路图是固定的；query 只决定你从哪站换乘、坐哪条线。

11.3 返回结果的格式是固定的吗？

外壳格式固定，里面填了什么因路径而异。 invoke 返回的始终是 WealthAdvisorState 风格的字典（同一套键）， 不是每种 query 换一种 JSON schema。
字段 含义 是否每次都有有效值
user_query / customer_profile 输入原样带回 是
query_type / processing_mode 评估阶段写入 是（评估成功时）
messages 反应式对话与工具历史 主要在反应式路径有内容
market_data / analysis_results 深思熟虑中间产物 主要在深思熟虑路径有内容
final_response 最终给用户的文本 两条路径都会写；内容随 LLM 变化
current_phase / error 控制与错误信息 视执行情况
  • 结构固定：调用方可以稳定读取 result["final_response"]、result["processing_mode"]。
  • 字段填充不固定：反应式时 market_data / analysis_results 多半仍是 None；深思熟虑时 messages 往往仍是空列表。
  • 文本内容不固定：final_response 是自然语言字符串，长度与写法随模型输出变化。
  • 内层 JSON 未强校验：如 analysis_results 由 Prompt + JsonOutputParser 约定，未用 Pydantic 强制校验，键可能略有波动。
对接上层时：以 final_response + processing_mode 为稳定契约； 不要假设两个分支的中间字段每次都齐全。

12. 实测运行记录

以下按实际执行步骤标注 Step1、Step2…；每步说明节点功能，并展示该节点 返回、写入 state 的 JSON 增量（与源码 return {...} 对应）。 数据来自 run_records.json（客户 customer1 / 平衡型）。

客户画像摘要：C10012345 / 平衡型 / 中期 / 组合 150 万；股票 40%、债券 30%、现金 10%、另类 20%。

案例 A · 反应式路径

问题：我的投资组合中股票占比是多少？

路径总览：assess → reactive_agent → tools → reactive_agent → extract_response → END

Step 1 assess / assess_query 情境评估与分流

协调层根据用户问题判断查询类型与处理模式，决定走反应式还是深思熟虑。本例判定为紧急查询 + 反应式。

本步返回 JSON（节点写入 state 的增量）
{
  "query_type": "emergency",
  "processing_mode": "reactive"
}
Step 2 reactive_agent 首次调用带工具 LLM

组装系统提示与用户问题，调用 llm_with_tools。本步尚未给出最终文本，而是发起工具调用 query_portfolio_allocation。

本步返回 JSON（节点写入 state 的增量）
{
  "messages": [
    {
      "type": "AIMessage",
      "content": "",
      "tool_calls": [
        {
          "name": "query_portfolio_allocation",
          "args": {
            "asset_type": "股票"
          },
          "id": "call_21f34e48854948b6b4126a",
          "type": "tool_call"
        }
      ]
    }
  ]
}
Step 3 tools / ToolNode 执行工具并回写结果

条件路由 should_continue_tools 发现存在 tool_calls，进入工具节点执行查询，将 ToolMessage 追加进 messages。

本步返回 JSON（节点写入 state 的增量）
{
  "messages": [
    {
      "type": "ToolMessage",
      "content": "股票在投资组合中的配置比例为: 40%",
      "name": "query_portfolio_allocation",
      "tool_call_id": "call_21f34e48854948b6b4126a"
    }
  ]
}
Step 4 reactive_agent 再次调用 LLM 生成回答

带着工具结果再次进入反应式节点；模型综合 ToolMessage 产出自然语言回答，此时无新的 tool_calls，路由转向提取响应。

本步返回 JSON（节点写入 state 的增量）
{
  "messages": [
    {
      "type": "AIMessage",
      "content": "股票在您的投资组合中的配置比例为 40%。如果您有任何调整的需求或者想要了解更多详情，请随时告诉我。"
    }
  ]
}
Step 5 extract_response / extract_reactive_response 提取最终回复并结束

从 messages 倒序找到最后一条有内容的 AIMessage，写入 final_response，随后进入 END。

本步返回 JSON（节点写入 state 的增量）
{
  "final_response": "股票在您的投资组合中的配置比例为 40%。如果您有任何调整的需求或者想要了解更多详情，请随时告诉我。"
}
案例 A 对照：评估后走反应式；中间靠 messages 累积工具调用； market_data / analysis_results 全程为 null。

案例 B · 深思熟虑路径

问题：根据当前市场情况，我应该如何调整投资组合以应对可能的经济衰退？

路径总览：assess → collect_data → analyze → recommend → END

Step 1 assess / assess_query 情境评估与分流

协调层判定本问需要深度分析，选择深思熟虑模式，条件边导向 collect_data。

本步返回 JSON（节点写入 state 的增量）
{
  "query_type": "analytical",
  "processing_mode": "deliberative"
}
Step 2 collect_data 数据收集

根据问题与客户画像，确定需收集的数据类型并生成（模拟）市场数据，写入 market_data，推进 phase 到 analyze。

Step 4 recommend / generate_recommendations 生成客户可读建议

将分析结果整理为面向客户的自然语言建议，写入 final_response，phase 记为 respond，随后进入 END。本路径 messages 保持为空。

本步返回 JSON（节点写入 state 的增量）
